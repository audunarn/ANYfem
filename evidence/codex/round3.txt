### Engineering doctrine

- Correctness and sound theory outrank speed.
- Hidden corrections, empirical gate-tuning, invented stiffness and silent
  fallback are prohibited.
- Ambiguity fails closed with a typed, actionable error.

## 2. Required development practice

1. Define the intended behavior, owner, compatibility impact and acceptance
   evidence before nontrivial implementation.
2. Keep changes narrow. Do not mix unrelated cleanup, formatting or capability
   expansion into the same change.
3. Treat AI output as untrusted input. A responsible contributor reviews every
   line, verifies licenses and provenance, and runs the same gates required for
   human-written work. Never provide secrets, customer data or restricted
   material to an unapproved model or service.
4. Preserve public compatibility. Breaking changes require an explicit ecosystem
   decision, migration path and later version-policy change; they cannot ship as
   a patch.
5. Never weaken a test, tolerance or validation rule merely to obtain a pass.

## 3. Testing gates

> **Merge rule:** all applicable gates must pass from a clean checkout.
> Select development checks by risk and impact; full release requirements remain
> release gates, not prerequisites for every Level-A experiment.

- Every behavior change has focused unit tests; every defect fix has a regression
  that fails without the fix.
- Public interfaces have contract tests. Cross-repository changes test both owner
  and consumer against declared supported versions.
- Numerical and physics changes include independent analytical, published or
  separately implemented references. Comparing code with itself is not
  qualification.
- Physics tests cover units, signs, frames, invariance, conservation/equilibrium,
  limiting cases, convergence and invalid inputs as applicable. Tolerances must
  follow theory or quantified numerical error, never observed output alone.
- Failure, cancellation, timeout, stale-data and fallback paths are tested.
  Fallback is permitted only when explicit, safe and reported.
- For supported delivery/release and changes affecting installed behavior,
  distributions are built and checked; an installed wheel is imported and
  smoke-tested outside the source tree. GUI/executable changes also receive a
  packaged-artifact smoke test on each claimed platform.
- Supported Python and operating-system claims are exercised in CI. A platform or
  version may be removed only by an explicit compatibility decision.
- Skips and expected failures require a recorded reason, owner and removal
  condition. Flaky tests are defects, not acceptable retries.
- Required CI must be green. A red, missing or cancelled gate is not evidence.

Documentation-only changes may use documentation/format checks when they cannot
affect runtime, packaging, commands or public contracts.

## 4. Qualification and traceability

Every qualification claim must identify:

- requirement, issue or decision and the exact qualified scope;
- repository, commit, tree, package version and dependency versions;
- commands, toolchain, Python, OS and relevant hardware;
- input identities, units, origins, licenses and SHA-256 hashes where practical;
- test and benchmark outputs, tolerances, limitations and failed/omitted cases;
- produced artifact identities and the reviewer/approver.

Evidence is immutable or content-addressed and reproducible from recorded inputs.
Generated, transformed and experimental data retain lineage. Standards, material
tables, reference results and third-party models require edition/source and
usage-rights records. Performance evidence never substitutes for correctness.
Claims must not exceed the executed matrix or reference quality.

## 5. Version and release policy

Versions use `MAJOR.MINOR.PATCH`.

> **Current release rule:** increment **PATCH only** until this policy is
> explicitly replaced.

- repository releases increment `A.B.X -> A.B.(X+1)`;
- major and minor increments are reserved and require a new ecosystem decision;
- patch releases must remain backward compatible; incompatible work is deferred
  or protected by a compatible migration/shim;
- package metadata, runtime `__version__`, tests, manifests and release
  documentation must agree;
- tags are `vA.B.X` and must match the built artifact version exactly;
- schemas and file formats carry their own versions and backward-read/migration
  rules; a package bump does not silently change a schema;
- PyPI publication always uses GitHub Actions OIDC Trusted Publishing. API tokens,
  passwords and manual credential uploads are prohibited.

A version bump does not prove qualification. Release requires the testing and
traceability gates above, reviewed artifacts, and explicit publication authority.

Decision-oriented investigation: before a substantial diagnostic batch, use the
existing living record to identify the question, competing explanations, bounded
experiment and how outcomes change the next action. Tie refinements, sweeps and
new reference tools to the principal uncertainty; interpret the combined evidence
and choose the next action rather than automatically repeating at greater cost.
This adds no registration, approval or reporting gate. Scientific acceptance
criteria and authority/resource limits remain unchanged; a spent diagnostic budget
does not prove formulation failure. See the canonical philosophy's
"Decision-oriented investigation" section.

# ANY Ecosystem Philosophy

## Canonical ownership

Each domain has one authoritative owner and dependencies flow downstream:

- ANYgeometry owns geometry, topology, persistent identity, tolerance,
  spatial indexing, intersections, and geometry audit truth.
- ANYmesh owns discretization and consumes qualified geometry contracts.
- ANYmaterial owns material definitions, validation, and canonical conventions.
- ANYio/ANYfileio owns interchange syntax and neutral file semantics.
- ANYfeSolver owns solver physics, numerical kernels, and qualification scope.
- ANYfem owns FEM workflow, projects, orchestration, and postprocessing.
- UI/application repositories consume public APIs and do not recreate domain truth.

Copied owner models, reverse imports, and coordinate-derived replacements for
owner topology are architectural defects. Compatibility facades may exist only
as thin, explicit, tested aliases.

## Contract doctrine

1. Prefer headless, public, stable contracts. Integration and UI layers use
   public APIs rather than private helpers.
2. Fail closed. Unsupported, unqualified, stale, wrong-model, or ambiguous
   inputs produce typed non-success; downstream preserves that truth.
3. Do not invent, narrow, or silently discard semantics. Preserve unknown
   interchange records, absent components, provenance, material symmetry, and
   solver-reported status.
4. Identity is model-bound and persistent. IDs are not guessed from coordinates,
   silently reused, or detached from revision/lineage.
5. Public mutation is atomic and rollback-safe. Incremental work follows explicit
   change sets and invalidation, not tolerance-based global rediscovery.
6. Boundary conventions are ecosystem contracts: SI internally, conversion once
   at ingestion/display, canonical material Voigt order, and structural protocols
   rather than concrete cross-package inheritance.

## Evidence and qualification

- Source and tests are behavioral truth. Reports are commit-, command-, and
  environment-scoped evidence, not timeless capability declarations.
- Qualification is narrower than implementation. A downstream application cannot
  broaden the solver owner's qualified scope.
- Partial runs, skipped execution, XFAIL, deck generation, and `not_executed` are
  never reported as passes.
- Failure evidence is retained. Plausible estimates, zeros, or fallbacks never
  replace a real non-success result.
- Every capability claim names the exact implementation identity, source SHA,
  contract version, command, result, platform, and remaining limits.

## Performance doctrine

Correctness and sound theory rank above performance. Implementations must be
physics-first where physics is involved and independently verifiable. Artificial
or hidden penalties, empirical tuning, invented stiffness, and other â€œmagicâ€
corrections may not be introduced merely to satisfy a numerical or performance
gate. A derived formulation requires an explicit identity, derivation,
provenance, and qualification.

Performance cannot change semantics. Every acceleration keeps a correctness
oracle, explicit eligibility, lifecycle, invalidation, deterministic diagnostics,
and fail-closed fallback rules. Timing alone does not prove activation or
correctness.

No production stage may retain demonstrated global-quadratic behavior where the
governing plan requires subquadratic scaling. Memory evidence distinguishes
Python-traced allocation from process RSS and native allocation. Performance
qualification follows the effective workspace resource policy and any task-specific
resource limits. In Normal-token mode, worker-owned scheduling applies under
`C:/Github/AGENTS.md`; historical lease rules do not reactivate themselves.

## Long-term stance

Prefer additive migration paths, explicit versions, and reversible compatibility.
Retire duplicated ownership rather than institutionalizing it. Frozen historical
trees remain historical and never regain authority through convenience imports.

## Adopted engineering and delivery policy

The following revision governs future development procedure across the ecosystem.
It supplements the ownership and technical doctrine above. Existing scientific,
release and task-specific execution boundaries remain in force as specified below.

### Risk-Proportionate Engineering and Delivery

**Policy ID:** `ANY_ECOSYSTEM_RISK_PROPORTIONATE_ENGINEERING_V1`

**Date:** 2026-09-24

**Status:** Adopted by user direction, effective 2026-09-24. Revision: `2026-09-24.2`. Canonical home: `ANYopenSoft/governance/ECOSYSTEM_PHILOSOPHY.md`.

**Scope:** All ANY packages, applications, research tools, integration workflows and participating human/AI development agents, including ECOboss coordination where used.

> **Develop iteratively, verify throughout, qualify the intended use, and preserve the evidence supporting the claim. Apply rigor to consequential failure modes; do not turn every development experiment into a qualification ceremony.**

### 1. Purpose and unchanged principles

Deliver useful, trustworthy engineering workflows. Measure progress by a working capability, a resolved uncertainty or a demonstrated improvementâ€”not by the number of plans, tests, agents, review rounds or archived files.

Scientific correctness, numerical honesty, user-data integrity and safe execution remain non-negotiable. Performance, lightweight deployment, maintainability, accessible interfaces and reproducibility remain primary design objectives. Optimize measured end-to-end work without silently changing the model, accuracy, admissible domain or reported meaning of results.

Preserve package ownership and interfaces. Reuse existing numerical kernels, transaction stores, geometry/topology services, material definitions, file formats and command layers before introducing competing infrastructure. Keep the open engineering packages independently useful; this update does not change any license or the boundary of proprietary products.

Scope assurance by **consequence, technical uncertainty, exposure and intended claim**, not by filename or project size. A research oracle, result-unit conversion or GUI command can be as consequential as a numerical kernel. Conversely, an isolated presentation change does not require a mechanics qualification programme.

This policy changes how development is organized. It does not itself qualify software, authorize a release, broaden an existing capability, waive a scientific requirement or override an explicit user restriction.

### 2. Assess risk and maturity separately

At the start of a substantial task, record the intended outcome, the consequential failure modes and the required acceptance evidence in the existing task note or pull request. A few sentences normally suffice; no new risk-scoring application or mandatory numerical risk score is required.

| Change risk | Typical examples | Proportionate assurance |
|---|---|---|
| Low, local and readily reversible | Editorial wording or layout with no change to numerical meaning, permissions or stored data | Normal review/CI and focused checks. No scientific acceptance dossier. |
| Behavioral or cross-package | New adapters, workflows, APIs, packaging or performance paths | Focused regression and end-to-end tests, compatibility review and honest capability documentation. Escalate where errors can silently change engineering results. |
| High consequence or difficult to detect | Mechanics, constitutive histories, units/frames, topology identity, constraints, numerical reference tools, uncertainty/fatigue calculations, restart, contact history, destructive migrations or privileged AI commands | Early risk-focused technical review, independent verification appropriate to the claim, and controlled acceptance before the changed behavior is relied upon. |

These examples are not automatic classifications. Reassess when exposure, dependencies, supported combinations or the proposed claim change. Explain a downgrade; do not relabel high-risk work merely to avoid a gate. Formal external obligations remain applicable.

Maturity is a separate dimension:

| Level | Purpose and permitted use | Minimum record and review |
|---|---|---|
| **A â€” Development and investigation** | Explore, implement, refactor, diagnose and run authorized integrated experiments. Results are provisional and cannot confer qualification. | Recoverable source, relevant tests, commands/inputs needed to reproduce important findings, and normal change review. Add early independent technical scrutiny for high-risk assumptions; do not require a formal acceptance package for every helper. |
| **B â€” Candidate acceptance** | Establish a named scientific, numerical, interoperability or performance claim within a declared domain. | Prospective criteria, exact candidate identity, controlled relevant runs, retained raw evidence and an independent acceptance assessment. Include a pre-run review when a governing contract or the risk requires it. |
| **C â€” Supported delivery or release** | Make the admitted capability available through a supported interface, artifact, default or release. | Impact-appropriate regression/qualification, matching installed-artifact checks, compatibility, recovery/restart/resource checks where applicable, release notes and the existing approval process. Reuse valid B evidence rather than regenerate it automatically. |

A routine low-risk patch does not need an artificial Level-B scientific study before release. High-risk development does not become low-risk because it lives under `scripts/`, is opt-in or is labelled experimental. Packaging, merge status, public exposure and scientific qualification remain distinct decisions.

### 3. Default development loop

Use the shortest loop that can establish the next meaningful result:

```text
Define the outcome and important failure modes
    -> inspect/reuse existing implementation and evidence
    -> implement a bounded end-to-end slice
    -> run local and integration checks
    -> investigate discrepancies with targeted independent checks
    -> retain the useful result or reject the approach
    -> repeat until a claim-bearing candidate is ready
```

Unit tests and small algebraic checks support this loop; they are not substitutes for exercising the assembled workflow. Run realistic integrated cases early enough to expose interface and modelling problems, inside the authorized execution scope and resource budget.

Do not automatically create a separate preregistration, immutable proof root, one-use adjudicator, source-binding framework or formal review milestone for each helper, bug fix or experiment. Use existing CI, test utilities and task records. A helper needs a separate authority package only when a concrete risk, reuse role or governing contract justifies it.

Use development commits and reproducible run records, not a mandatory fixed commit count. New experiments may be rerun and redesigned unless a specific restriction applies. Record material changes and failures; do not repeatedly rerun a nondeterministic test until it happens to pass.

A blocked exploratory attempt should normally produce a diagnosis and a bounded next action. Reserve fail-closed acceptance behavior for the trust boundary: invalid or unsupported results must not be used or presented as qualified. Do not disable runtime safety/capability guards to speed development; isolate a deliberately diagnostic route when necessary.

#### Decision-oriented investigation

Organize exploratory work around the decision it must enable. Before a
substantial diagnostic batch, briefly identify the unresolved question,
the competing explanations, the bounded experiment that distinguishes
them, and how its possible outcomes affect the next action.

Repeated refinement, parameter sweeps or additional reference tooling
require a stated reason tied to the principal uncertainty. At the end
of a batch, interpret the combined evidence and decide whether to
continue, change the approach, advance an independent workstream, or
report a specific unresolved limitation. Do not automatically repeat
the same experiment at greater cost.

Use the existing living task record; this is not a new registration,
approval or reporting gate. Developers retain discretion within their
authority and resource limits. Diagnostic stopping rules do not replace
scientific acceptance criteria, and exhausting a diagnostic budget does
not prove that a formulation has failed.

### 4. Review where it can change the decision

Normal engineering review remains part of development. Independent review is not forbidden at Level A and must not be postponed until release when a high-risk assumption will shape the implementation or the next experiment.

Prefer one review owner coordinating the relevant expertise and reusing resolved findings. Add specialist review for concrete mechanics, numerics, security or interoperability risks. Do not require a fixed agent count, multiple model votes or repeated complete rereviews after unrelated edits. Review changed and affected areas; widen the review when their dependencies justify it.

A useful independent check can be an analytical result, separately derived formulation, manufactured-work calculation, different integration/solution route, derivative oracle or compatible external reference. Match it to the claim. Two wrappers around the same implementation are not independent verification. Two AI agents or differently named scripts do not by themselves establish scientific independence or human approval.

Reviewers should distinguish a correctness blocker from a documentation clarification and an optional improvement. An additional blocking control must identify the failure mode it addresses and the decision it affects. This is not a restriction on discovering defects; it prevents unrelated framework expansion from becoming a completion condition.

### 5. Candidate acceptance: define criteria before the assessment run

The earlier shorthand â€œfreeze claims, not experimentsâ€ is replaced by this more precise rule:

> **Explore freely within authority. Define and freeze the acceptance question, inputs, metrics and criteria before the formal assessment. Preserve the complete evidence when accepting or rejecting the claim.**

For a scientific/numerical candidate, the concise acceptance plan must identify the physical or mathematical problem, admitted domain, source/data identity, solver options, relevant integration and scaling, observables, reference/oracle, tolerances, resource limits, failure handling and result interpretation. Include conditioning, mesh/time refinement, state history or work/energy checks where they are materialâ€”not as a universal checklist for every change.

Known development cases may remain regression benchmarks. Disclose that they informed development; do not call them blind validation. Do not retrofit acceptance limits to observed candidate values. A justified change to an acceptance criterion requires an explicit new decision and prospective assessment; the previous failed result remains failed under its original criterion.

A candidate package ordinarily needs one source/environment record, one relevant run collection, and one acceptance report. Source-control identity plus hashes for built or externally stored artifacts can establish provenance without copying and hashing every helper repeatedly. Reuse stricter existing machinery when a current contract requires it.

Retain actual invoked commands, exit status, relevant inputs, seeds, environment/thread/backend settings and raw quantities sufficient to recompute the verdict. Record the built/installed artifact when installation is part of the claim. Do not report a generated deck as an executed comparison, a small residual as physical accuracy, or a successful reference calculation as qualification of a different product.

An independent assessment must address correctness, numerical adequacy, contrary evidence and the scope of the conclusionâ€”not merely file hashes. If a formal run fails, preserve it, return to development, and assess a corrected candidate under a clearly identified revision. Do not restart the entire historical qualification programme unless the affected dependencies require it.

### 6. Minimum evidence without indiscriminate archiving

Git preserves committed content, not every untracked log, external result or active worktree. Important evidence therefore needs an explicit home. [R3]

For development, retain the minimal reproducible counterexample or fixture, the affected source identity, the observed failure and the fix/regression test. Keep raw data when necessary to understand or reproduce a consequential finding. An exhaustive permanent archive of every terminal message and successful intermediate run is not required.

Do not selectively discard negative results that challenge a later claim. Repetitive transient logs may follow the ordinary retention policy once meaningful failures, decisions and required inputs are retained. This policy is not authorization to delete historical archives, user files or another worker's outputs.

For accepted claims, preserve exact artifacts and enough evidence to reproduce the decision. Use one maintainable manifest where appropriate, rather than recursive inventories of inventories. Bitwise reproducibility is required when it is part of the declared contract or necessary for identity; otherwise specify the appropriate numerical reproducibility across supported environments. Existing exact-equality obligations cannot be relaxed implicitly.

A checksum proves identity, not physical correctness. A test count proves neither coverage nor an admitted engineering domain. A previous proof applies only to its actual assumptions, implementation and data.

### 7. Scientific and safety boundaries that remain unchanged

Never silently alter equations, physical geometry, reference frames, units, load/support definitions, constraints, constitutive state laws, prescribed inertia, reference data, observables, acceptance tolerances or error normalizations to achieve a pass. Numerical changes are permitted when deliberately implemented and assessed as changesâ€”not disguised as administrative simplification.

Preserve committed/trial ownership, rollback, restart compatibility, capability checks, conservation/work identities where applicable and explicit rejection of unsupported combinations. A faster execution path must retain its stated numerical contract or receive a separately assessed scope.

Reference code and adjudication code require assurance commensurate with the product conclusions that depend on them. Calling a reference implementation â€œresearch toolingâ€ does not reduce its consequence. Exact arithmetic and certified error bounds remain necessary where the registered question requires them; they are not blanket prerequisites for unrelated exploration.

Keep source-reading, test execution, benchmark performance, mathematical verification, physical validation and product release claims separate. Report uncertainty, unresolved numerical admission and nonconvergence honestly. A failed upper-bound certificate is not automatically a demonstrated mechanics defect.

This update does not relax licensing, privacy, credential handling, file permissions, network restrictions, paid-resource approvals or destructive-operation controls.

### 8. Reuse evidence through impact analysis

Before rerunning a large campaign, identify the changed behavior and its dependents. Reuse accepted evidence only when the relevant implementation, inputs, assumptions and numerical environment remain applicable. Record why the evidence still applies; do not relabel an old run as execution of a new artifact.

A documentation-only change normally needs documentation checks, not a new mechanics campaign. A change to a shared return map, frame convention, state owner, parser-unit map or constraint reduction may require broad downstream revalidation. A default/selector change requires explicit scope and compatibility review even if kernel equations are unchanged.

Respect current release requirements. A partial development suite cannot replace a required full release suite. Any change to such a requirement must be explicitly adopted before it is used, not excused after a failure. The current ANYfeSolver quality guide already separates development diagnosis from full release evidence. [R4]

### 9. Performance, resources and practical completion

Profile complete workflows and cost per accepted result, including failed steps, repeated evaluations, setup, state copies, recovery and serialization. Keep measurement overhead bounded. Prefer simpler proven optimizations to speculative rewrites or new mandatory dependencies.

Tests and experiments must fit declared CPU/GPU, memory, disk, thread and execution permissions. Account for child processes and large factorization/output workspaces when relevant. Development reruns do not imply unlimited compute authority. A resource limit may stop a run, but does not establish physical failure or a successful scientific criterion.

Maintain one short living task record: outcome, actual state, next integrated result, decisive checks, material findings and remaining blocker. Extend an existing record instead of creating one file per item. If checkpoints keep producing only helper infrastructure without reducing the principal uncertainty, simplify the next experiment or escalate that specific obstruction. Do not invent a new framework as the default response.

Reuse existing publication, CI and packaging infrastructure. Do not make a universal certificate engine, general benchmark platform or new governance service a prerequisite for a bounded engineering result unless the actual task requires it.

### 10. Agent execution and authority

The integration owner coordinates shared files, compatibility and final disposition. Use bounded specialist assignments and isolated worktrees when concurrent work requires them. Group independent reads/tests when efficient. Avoid repeated polling without a decision need. Model names, effort settings and spending follow the user's actual choice; do not silently escalate or claim unobservable settings.

ECOboss or another coordinator applies this policy only within delegated authority. It cannot manufacture approval, silently change an active task's contract, waive scientific criteria, or grant itself broader filesystem/network/release permissions.

Preserve protected branches, unrelated changes, in-flight runs, committed evidence and worktree ownership. Do not reset, clean, rebase, merge, publish or terminate another worker merely to obtain a convenient baseline. Check actual state before acting; a cached remote reference is not a fresh remote verification.

A numerical failure, unsupported case or authorization conflict should stop the affected action, not automatically stop every independent part of the task. Continue permitted useful work while clearly identifying the blocked boundary.

### 11. Adopting the policy and migrating active tasks

**Implementation order: ecosystem policy first, task steering second.**

1. Locate and read the actual canonical ecosystem philosophy and the instructions used by its orchestrator and repositories. Merge this policy into that authority; do not create a competing philosophy by guessing a path. If no canonical location exists, the owner selects one and records it.
2. Retain the policy ID above as a stable searchable anchor. Record the adopted file path and commit/revision. Set its effective status through the existing approval process. Update relevant instruction pointers or explicitly distribute the adopted document to workers that cannot access it. Prefer references to one authority over divergent copies.
3. Preserve unrelated philosophy, licenses, technical requirements and release rules. Remove or amend blanket *future administrative* requirements only where this policy explicitly replaces them. Do not rewrite completed contracts or archives.
4. For each active task, add one short prospective transition note to its existing plan: adopted policy reference; administrative steps consolidated; substantive gates retained; next permitted integrated action; and any remaining approval required. Obtain task-owner authorization where its current contract requires amendment. Do not create another full qualification package for this transition.
5. Give the worker an explicit steering instruction to read the adopted policy and the transition note. Do not assume a running agent automatically reloads changed instruction files. Verify that the worker names the same policy revision and retained acceptance boundaries before it changes its process.

**Conflict rule:** this general policy does not silently supersede a frozen case registration, consumed one-use execution, resource approval, explicit no-run instruction or protected evidence requirement. Amend future procedural requirements explicitly. Keep scientific criteria and historical dispositions intact unless separately changed by the proper authority. When blocked, identify the exact conflict and the smallest required decision; do not ask for approval after every ordinary development action.

### 12. Definition of completion

A task is complete when the requested end-to-end outcome works within its declared domain, relevant correctness and compatibility checks pass, risk-appropriate review is closed, results are reproducible at the required level, and any remaining limitations are accurately exposed. Publication and default changes need their own existing authorization.

A qualification claim requires its specified acceptance evidence. A development task may also close with a supported negative conclusion or a precisely documented unresolved limitation. Neither documentation volume nor a test count substitutes for the requested result.

Suggested entry in the existing task record:

```text
Outcome and intended use:
Risk / acceptance level, with reason:
Current implementation and evidence:
Next integrated test or result:
Unchanged criteria / authority / resource limits:
Material findings and affected dependencies:
Decision and remaining limitation:
```

# ANY Ecosystem Philosophy

## Canonical ownership

Each domain has one authoritative owner and dependencies flow downstream:

- ANYgeometry owns geometry, topology, persistent identity, tolerance,
  spatial indexing, intersections, and geometry audit truth.
- ANYmesh owns discretization and consumes qualified geometry contracts.
- ANYmaterial owns material definitions, validation, and canonical conventions.
- ANYio/ANYfileio owns interchange syntax and neutral file semantics.
- ANYfeSolver owns solver physics, numerical kernels, and qualification scope.
- ANYfem owns FEM workflow, projects, orchestration, and postprocessing.
- UI/application repositories consume public APIs and do not recreate domain truth.

Copied owner models, reverse imports, and coordinate-derived replacements for
owner topology are architectural defects. Compatibility facades may exist only
as thin, explicit, tested aliases.

## Contract doctrine

1. Prefer headless, public, stable contracts. Integration and UI layers use
   public APIs rather than private helpers.
2. Fail closed. Unsupported, unqualified, stale, wrong-model, or ambiguous
   inputs produce typed non-success; downstream preserves that truth.
3. Do not invent, narrow, or silently discard semantics. Preserve unknown
   interchange records, absent components, provenance, material symmetry, and
   solver-reported status.
4. Identity is model-bound and persistent. IDs are not guessed from coordinates,
   silently reused, or detached from revision/lineage.
5. Public mutation is atomic and rollback-safe. Incremental work follows explicit
   change sets and invalidation, not tolerance-based global rediscovery.
6. Boundary conventions are ecosystem contracts: SI internally, conversion once
   at ingestion/display, canonical material Voigt order, and structural protocols
   rather than concrete cross-package inheritance.

## Evidence and qualification

- Source and tests are behavioral truth. Reports are commit-, command-, and
  environment-scoped evidence, not timeless capability declarations.
- Qualification is narrower than implementation. A downstream application cannot
  broaden the solver owner's qualified scope.
- Partial runs, skipped execution, XFAIL, deck generation, and `not_executed` are
  never reported as passes.
- Failure evidence is retained. Plausible estimates, zeros, or fallbacks never
  replace a real non-success result.
- Every capability claim names the exact implementation identity, source SHA,
  contract version, command, result, platform, and remaining limits.

## Performance doctrine

Correctness and sound theory rank above performance. Implementations must be
physics-first where physics is involved and independently verifiable. Artificial
or hidden penalties, empirical tuning, invented stiffness, and other â€œmagicâ€
corrections may not be introduced merely to satisfy a numerical or performance
gate. A derived formulation requires an explicit identity, derivation,
provenance, and qualification.

Performance cannot change semantics. Every acceleration keeps a correctness
oracle, explicit eligibility, lifecycle, invalidation, deterministic diagnostics,
and fail-closed fallback rules. Timing alone does not prove activation or
correctness.

No production stage may retain demonstrated global-quadratic behavior where the
governing plan requires subquadratic scaling. Memory evidence distinguishes
Python-traced allocation from process RSS and native allocation. Performance
qualification follows the effective workspace resource policy and any task-specific
resource limits. In Normal-token mode, worker-owned scheduling applies under
`C:/Github/AGENTS.md`; historical lease rules do not reactivate themselves.

## Long-term stance

Prefer additive migration paths, explicit versions, and reversible compatibility.
Retire duplicated ownership rather than institutionalizing it. Frozen historical
trees remain historical and never regain authority through convenience imports.

## Adopted engineering and delivery policy

The following revision governs future development procedure across the ecosystem.
It supplements the ownership and technical doctrine above. Existing scientific,
release and task-specific execution boundaries remain in force as specified below.

### Risk-Proportionate Engineering and Delivery

**Policy ID:** `ANY_ECOSYSTEM_RISK_PROPORTIONATE_ENGINEERING_V1`

**Date:** 2026-09-24

**Status:** Adopted by user direction, effective 2026-09-24. Revision: `2026-09-24.2`. Canonical home: `ANYopenSoft/governance/ECOSYSTEM_PHILOSOPHY.md`.

**Scope:** All ANY packages, applications, research tools, integration workflows and participating human/AI development agents, including ECOboss coordination where used.

> **Develop iteratively, verify throughout, qualify the intended use, and preserve the evidence supporting the claim. Apply rigor to consequential failure modes; do not turn every development experiment into a qualification ceremony.**

### 1. Purpose and unchanged principles

Deliver useful, trustworthy engineering workflows. Measure progress by a working capability, a resolved uncertainty or a demonstrated improvementâ€”not by the number of plans, tests, agents, review rounds or archived files.

Scientific correctness, numerical honesty, user-data integrity and safe execution remain non-negotiable. Performance, lightweight deployment, maintainability, accessible interfaces and reproducibility remain primary design objectives. Optimize measured end-to-end work without silently changing the model, accuracy, admissible domain or reported meaning of results.

Preserve package ownership and interfaces. Reuse existing numerical kernels, transaction stores, geometry/topology services, material definitions, file formats and command layers before introducing competing infrastructure. Keep the open engineering packages independently useful; this update does not change any license or the boundary of proprietary products.

Scope assurance by **consequence, technical uncertainty, exposure and intended claim**, not by filename or project size. A research oracle, result-unit conversion or GUI command can be as consequential as a numerical kernel. Conversely, an isolated presentation change does not require a mechanics qualification programme.

This policy changes how development is organized. It does not itself qualify software, authorize a release, broaden an existing capability, waive a scientific requirement or override an explicit user restriction.

### 2. Assess risk and maturity separately

At the start of a substantial task, record the intended outcome, the consequential failure modes and the required acceptance evidence in the existing task note or pull request. A few sentences normally suffice; no new risk-scoring application or mandatory numerical risk score is required.

| Change risk | Typical examples | Proportionate assurance |
|---|---|---|
| Low, local and readily reversible | Editorial wording or layout with no change to numerical meaning, permissions or stored data | Normal review/CI and focused checks. No scientific acceptance dossier. |
| Behavioral or cross-package | New adapters, workflows, APIs, packaging or performance paths | Focused regression and end-to-end tests, compatibility review and honest capability documentation. Escalate where errors can silently change engineering results. |
| High consequence or difficult to detect | Mechanics, constitutive histories, units/frames, topology identity, constraints, numerical reference tools, uncertainty/fatigue calculations, restart, contact history, destructive migrations or privileged AI commands | Early risk-focused technical review, independent verification appropriate to the claim, and controlled acceptance before the changed behavior is relied upon. |

These examples are not automatic classifications. Reassess when exposure, dependencies, supported combinations or the proposed claim change. Explain a downgrade; do not relabel high-risk work merely to avoid a gate. Formal external obligations remain applicable.

Maturity is a separate dimension:

| Level | Purpose and permitted use | Minimum record and review |
|---|---|---|
| **A â€” Development and investigation** | Explore, implement, refactor, diagnose and run authorized integrated experiments. Results are provisional and cannot confer qualification. | Recoverable source, relevant tests, commands/inputs needed to reproduce important findings, and normal change review. Add early independent technical scrutiny for high-risk assumptions; do not require a formal acceptance package for every helper. |
| **B â€” Candidate acceptance** | Establish a named scientific, numerical, interoperability or performance claim within a declared domain. | Prospective criteria, exact candidate identity, controlled relevant runs, retained raw evidence and an independent acceptance assessment. Include a pre-run review when a governing contract or the risk requires it. |
| **C â€” Supported delivery or release** | Make the admitted capability available through a supported interface, artifact, default or release. | Impact-appropriate regression/qualification, matching installed-artifact checks, compatibility, recovery/restart/resource checks where applicable, release notes and the existing approval process. Reuse valid B evidence rather than regenerate it automatically. |

A routine low-risk patch does not need an artificial Level-B scientific study before release. High-risk development does not become low-risk because it lives under `scripts/`, is opt-in or is labelled experimental. Packaging, merge status, public exposure and scientific qualification remain distinct decisions.

### 3. Default development loop

Use the shortest loop that can establish the next meaningful result:

```text
Define the outcome and important failure modes
    -> inspect/reuse existing implementation and evidence
    -> implement a bounded end-to-end slice
    -> run local and integration checks
    -> investigate discrepancies with targeted independent checks
    -> retain the useful result or reject the approach
    -> repeat until a claim-bearing candidate is ready
```

Unit tests and small algebraic checks support this loop; they are not substitutes for exercising the assembled workflow. Run realistic integrated cases early enough to expose interface and modelling problems, inside the authorized execution scope and resource budget.

Do not automatically create a separate preregistration, immutable proof root, one-use adjudicator, source-binding framework or formal review milestone for each helper, bug fix or experiment. Use existing CI, test utilities and task records. A helper needs a separate authority package only when a concrete risk, reuse role or governing contract justifies it.

Use development commits and reproducible run records, not a mandatory fixed commit count. New experiments may be rerun and redesigned unless a specific restriction applies. Record material changes and failures; do not repeatedly rerun a nondeterministic test until it happens to pass.

A blocked exploratory attempt should normally produce a diagnosis and a bounded next action. Reserve fail-closed acceptance behavior for the trust boundary: invalid or unsupported results must not be used or presented as qualified. Do not disable runtime safety/capability guards to speed development; isolate a deliberately diagnostic route when necessary.

#### Decision-oriented investigation

Organize exploratory work around the decision it must enable. Before a
substantial diagnostic batch, briefly identify the unresolved question,
the competing explanations, the bounded experiment that distinguishes
them, and how its possible outcomes affect the next action.

Repeated refinement, parameter sweeps or additional reference tooling
require a stated reason tied to the principal uncertainty. At the end
of a batch, interpret the combined evidence and decide whether to
continue, change the approach, advance an independent workstream, or
report a specific unresolved limitation. Do not automatically repeat
the same experiment at greater cost.

Use the existing living task record; this is not a new registration,
approval or reporting gate. Developers retain discretion within their
authority and resource limits. Diagnostic stopping rules do not replace
scientific acceptance criteria, and exhausting a diagnostic budget does
not prove that a formulation has failed.

### 4. Review where it can change the decision

Normal engineering review remains part of development. Independent review is not forbidden at Level A and must not be postponed until release when a high-risk assumption will shape the implementation or the next experiment.

Prefer one review owner coordinating the relevant expertise and reusing resolved findings. Add specialist review for concrete mechanics, numerics, security or interoperability risks. Do not require a fixed agent count, multiple model votes or repeated complete rereviews after unrelated edits. Review changed and affected areas; widen the review when their dependencies justify it.

A useful independent check can be an analytical result, separately derived formulation, manufactured-work calculation, different integration/solution route, derivative oracle or compatible external reference. Match it to the claim. Two wrappers around the same implementation are not independent verification. Two AI agents or differently named scripts do not by themselves establish scientific independence or human approval.

Reviewers should distinguish a correctness blocker from a documentation clarification and an optional improvement. An additional blocking control must identify the failure mode it addresses and the decision it affects. This is not a restriction on discovering defects; it prevents unrelated framework expansion from becoming a completion condition.

### 5. Candidate acceptance: define criteria before the assessment run

The earlier shorthand â€œfreeze claims, not experimentsâ€ is replaced by this more precise rule:

> **Explore freely within authority. Define and freeze the acceptance question, inputs, metrics and criteria before the formal assessment. Preserve the complete evidence when accepting or rejecting the claim.**

For a scientific/numerical candidate, the concise acceptance plan must identify the physical or mathematical problem, admitted domain, source/data identity, solver options, relevant integration and scaling, observables, reference/oracle, tolerances, resource limits, failure handling and result interpretation. Include conditioning, mesh/time refinement, state history or work/energy checks where they are materialâ€”not as a universal checklist for every change.

Known development cases may remain regression benchmarks. Disclose that they informed development; do not call them blind validation. Do not retrofit acceptance limits to observed candidate values. A justified change to an acceptance criterion requires an explicit new decision and prospective assessment; the previous failed result remains failed under its original criterion.

A candidate package ordinarily needs one source/environment record, one relevant run collection, and one acceptance report. Source-control identity plus hashes for built or externally stored artifacts can establish provenance without copying and hashing every helper repeatedly. Reuse stricter existing machinery when a current contract requires it.

Retain actual invoked commands, exit status, relevant inputs, seeds, environment/thread/backend settings and raw quantities sufficient to recompute the verdict. Record the built/installed artifact when installation is part of the claim. Do not report a generated deck as an executed comparison, a small residual as physical accuracy, or a successful reference calculation as qualification of a different product.

An independent assessment must address correctness, numerical adequacy, contrary evidence and the scope of the conclusionâ€”not merely file hashes. If a formal run fails, preserve it, return to development, and assess a corrected candidate under a clearly identified revision. Do not restart the entire historical qualification programme unless the affected dependencies require it.

### 6. Minimum evidence without indiscriminate archiving

Git preserves committed content, not every untracked log, external result or active worktree. Important evidence therefore needs an explicit home. [R3]

For development, retain the minimal reproducible counterexample or fixture, the affected source identity, the observed failure and the fix/regression test. Keep raw data when necessary to understand or reproduce a consequential finding. An exhaustive permanent archive of every terminal message and successful intermediate run is not required.

Do not selectively discard negative results that challenge a later claim. Repetitive transient logs may follow the ordinary retention policy once meaningful failures, decisions and required inputs are retained. This policy is not authorization to delete historical archives, user files or another worker's outputs.

For accepted claims, preserve exact artifacts and enough evidence to reproduce the decision. Use one maintainable manifest where appropriate, rather than recursive inventories of inventories. Bitwise reproducibility is required when it is part of the declared contract or necessary for identity; otherwise specify the appropriate numerical reproducibility across supported environments. Existing exact-equality obligations cannot be relaxed implicitly.

A checksum proves identity, not physical correctness. A test count proves neither coverage nor an admitted engineering domain. A previous proof applies only to its actual assumptions, implementation and data.

### 7. Scientific and safety boundaries that remain unchanged

Never silently alter equations, physical geometry, reference frames, units, load/support definitions, constraints, constitutive state laws, prescribed inertia, reference data, observables, acceptance tolerances or error normalizations to achieve a pass. Numerical changes are permitted when deliberately implemented and assessed as changesâ€”not disguised as administrative simplification.

Preserve committed/trial ownership, rollback, restart compatibility, capability checks, conservation/work identities where applicable and explicit rejection of unsupported combinations. A faster execution path must retain its stated numerical contract or receive a separately assessed scope.

Reference code and adjudication code require assurance commensurate with the product conclusions that depend on them. Calling a reference implementation â€œresearch toolingâ€ does not reduce its consequence. Exact arithmetic and certified error bounds remain necessary where the registered question requires them; they are not blanket prerequisites for unrelated exploration.

Keep source-reading, test execution, benchmark performance, mathematical verification, physical validation and product release claims separate. Report uncertainty, unresolved numerical admission and nonconvergence honestly. A failed upper-bound certificate is not automatically a demonstrated mechanics defect.

This update does not relax licensing, privacy, credential handling, file permissions, network restrictions, paid-resource approvals or destructive-operation controls.

### 8. Reuse evidence through impact analysis

Before rerunning a large campaign, identify the changed behavior and its dependents. Reuse accepted evidence only when the relevant implementation, inputs, assumptions and numerical environment remain applicable. Record why the evidence still applies; do not relabel an old run as execution of a new artifact.

A documentation-only change normally needs documentation checks, not a new mechanics campaign. A change to a shared return map, frame convention, state owner, parser-unit map or constraint reduction may require broad downstream revalidation. A default/selector change requires explicit scope and compatibility review even if kernel equations are unchanged.

Tests and experiments must fit declared CPU/GPU, memory, disk, thread and execution permissions. Account for child processes and large factorization/output workspaces when relevant. Development reruns do not imply unlimited compute authority. A resource limit may stop a run, but does not establish physical failure or a successful scientific criterion.

Maintain one short living task record: outcome, actual state, next integrated result, decisive checks, material findings and remaining blocker. Extend an existing record instead of creating one file per item. If checkpoints keep producing only helper infrastructure without reducing the principal uncertainty, simplify the next experiment or escalate that specific obstruction. Do not invent a new framework as the default response.

Reuse existing publication, CI and packaging infrastructure. Do not make a universal certificate engine, general benchmark platform or new governance service a prerequisite for a bounded engineering result unless the actual task requires it.

The integration owner coordinates shared files, compatibility and final disposition. Use bounded specialist assignments and isolated worktrees when concurrent work requires them. Group independent reads/tests when efficient. Avoid repeated polling without a decision need. Model names, effort settings and spending follow the user's actual choice; do not silently escalate or claim unobservable settings.

Do not reset, clean, rebase, merge, publish or terminate another worker merely to obtain a convenient baseline. Check actual state before acting; a cached remote reference is not a fresh remote verification.

A numerical failure, unsupported case or authorization conflict should stop the affected action, not automatically stop every independent part of the task. Continue permitted useful work while clearly identifying the blocked boundary.

### 3. Default development loop

Use the shortest loop that can establish the next meaningful result:

```text

    -> inspect/reuse existing implementation and evidence
    -> implement a bounded end-to-end slice
    -> run local and integration checks
    -> investigate discrepancies with targeted independent checks
    -> retain the useful result or reject the approach
    -> repeat until a claim-bearing candidate is ready
```

Unit tests and small algebraic checks support this loop; they are not substitutes for exercising the assembled workflow. Run realistic integrated cases early enough to expose interface and modelling problems, inside the authorized execution scope and resource budget.

Do not automatically create a separate preregistration, immutable proof root, one-use adjudicator, source-binding framework or formal review milestone for each helper, bug fix or experiment. Use existing CI, test utilities and task records. A helper needs a separate authority package only when a concrete risk, reuse role or governing contract justifies it.

Use development commits and reproducible run records, not a mandatory fixed commit count. New experiments may be rerun and redesigned unless a specific restriction applies. Record material changes and failures; do not repeatedly rerun a nondeterministic test until it happens to pass.

A blocked exploratory attempt should normally produce a diagnosis and a bounded next action. Reserve fail-closed acceptance behavior for the trust boundary: invalid or unsupported results must not be used or presented as qualified. Do not disable runtime safety/capability guards to speed development; isolate a deliberately diagnostic route when necessary.

#### Decision-oriented investigation

Organize exploratory work around the decision it must enable. Before a
substantial diagnostic batch, briefly identify the unresolved question,
the competing explanations, the bounded experiment that distinguishes
them, and how its possible outcomes affect the next action.

Repeated refinement, parameter sweeps or additional reference tooling

of a batch, interpret the combined evidence and decide whether to
continue, change the approach, advance an independent workstream, or
report a specific unresolved limitation. Do not automatically repeat
the same experiment at greater cost.

Use the existing living task record; this is not a new registration,
approval or reporting gate. Developers retain discretion within their
authority and resource limits. Diagnostic stopping rules do not replace
scientific acceptance criteria, and exhausting a diagnostic budget does
not prove that a formulation has failed.

### 4. Review where it can change the decision

Normal engineering review remains part of development. Independent review is not forbidden at Level A and must not be postponed until release when a high-risk assumption will shape the implementation or the next experiment.

Prefer one review owner coordinating the relevant expertise and reusing resolved findings. Add specialist review for concrete mechanics, numerics, security or interoperability risks. Do not require a fixed agent count, multiple model votes or repeated complete rereviews after unrelated edits. Review changed and affected areas; widen the review when their dependencies justify it.

A useful independent check can be an analytical result, separately derived formulation, manufactured-work calculation, different integration/solution route, derivative oracle or compatible external reference. Match it to the claim. Two wrappers around the same implementation are not independent verification. Two AI agents or differently named scripts do not by themselves establish scientific independence or human approval.

Reviewers should distinguish a correctness blocker from a documentation clarification and an optional improvement. An additional blocking control must identify the failure mode it addresses and the decision it affects. This is not a restriction on discovering defects; it prevents unrelated framework expansion from becoming a completion condition.

class SolvedGeometry:
    """The FE model a result's displacements are measured from, or a refusal."""

    __slots__ = ("_model", "_refusal")

    def __init__(self, *, model: Any = None, refusal: Optional[str] = None) -> None:
        if (model is None) == (refusal is None):
            raise ValueError("SolvedGeometry needs exactly one of a model or a refusal")
        self._model = model
        self._refusal = refusal

    # ------------------------------------------------------------------
    @classmethod
    def exact(cls, model: Any) -> "SolvedGeometry":
        """Bind to the model object the solver returned as solved."""

        return cls(model=model)

    @classmethod
    def refused(cls, reason: str) -> "SolvedGeometry":
        """A binding that refuses recovery, e.g. for views of an unbound result."""

        return cls(refusal=str(reason))

    @classmethod
    def rebuild(cls, base_model: Any, imperfection_field: Any, raw_result: Any,
                *, context: str) -> Optional["SolvedGeometry"]:
        """Bind to ``base_model`` plus the run-time imperfection the solver applied.

        Call this straight after the solve, with the owned snapshot from
        :func:`owned_imperfection_field` that was also the object handed to the
        solver -- so solve and recovery consume one conversion.  The copy is
        made here, eagerly, so later edits to the built model (coordinates,
        thickness, materials, connectivity) cannot leak into it: it is the same
        deep copy of the same model state the solver made, moved by the same
        offsets through the same :func:`apply_imperfection`.  Returns ``None``
        when every offset is exactly zero: the solved coordinates are then the
        base coordinates bit for bit, and the ordinary route stays untouched.
        """

        from anyfesolver.imperfections import ImperfectionField

        if not isinstance(imperfection_field, ImperfectionField):
            raise TypeError("rebuild needs the owned ImperfectionField given to the solver")
        records = _solver_imperfection_records(raw_result)
        build_records = _records(getattr(base_model, "imperfection_metadata", None))
        expected = {"name": imperfection_field.name, "max_offset": imperfection_field.max_offset}
        if (
            records is None
            or len(records) != len(build_records) + 1
            or not all(_same_record(a, b) for a, b in zip(records, build_records))
            or not _same_record(records[-1], expected)
        ):
            raise UnboundSolvedGeometryError(
                f"{context}: the solver's imperfection record {records!r} does not "
                f"match the build-time imperfections {build_records!r} plus the "
                f"run-time imperfection {expected!r}; the solved geometry cannot be "
                "reproduced, so no stresses are recovered on it"
            )
        if not _has_offset(imperfection_field):
            return None
        from anyfesolver import apply_imperfection

        return cls(model=apply_imperfection(base_model, imperfection_field, copy_model=True))

    # ------------------------------------------------------------------
    def model(self) -> Any:
        """The solved FE model; raises when this binding is a refusal."""

        if self._refusal is not None:
            raise UnboundSolvedGeometryError(self._refusal)
        return self._model

    def __getstate__(self):
        return (self._model, self._refusal)

    def __setstate__(self, state) -> None:
        self._model, self._refusal = state


def _runtime_imperfection_unbound(view: Any) -> Optional[str]:
    records = _solver_imperfection_records(getattr(view, "raw_result", None))
    if records is not None:
        build_records = _records(getattr(view.built.fe_model, "imperfection_metadata", None))
        runtime = records[len(build_records):]
        if any(float(entry.get("max_offset", np.nan)) != 0.0 for entry in runtime):
            return "a run-time imperfection"
    info = getattr(view, "info", None)
    workflow = info.get("raw") if isinstance(info, Mapping) else None
    imperfect = getattr(workflow, "imperfect_model", None)
    if imperfect is not None and imperfect is not view.built.fe_model:
        field = getattr(workflow, "imperfection", None)
        if field is None or _has_offset(field):
            return "the capacity workflow's imperfection"
    return None


def unbound_refusal(view: Any) -> Optional[str]:
    """The refusal message for an imperfect result without a binding, if any."""

    reason = _runtime_imperfection_unbound(view)
    if reason is None:
        return None
    return (
        f"this result was solved on geometry moved by {reason}, but it carries "
        "no binding to that solved model; stresses recovered on the perfect "
        "built model would be wrong, so recovery is refused"
    )


def solved_model_of(view: Any) -> Any:
    """The FE model to recover ``view``'s displacements on.

    Views without a binding use ``built.fe_model``, exactly as before -- unless
    their solver record says the solve ran on imperfect geometry that is not
    in ``built.fe_model``, which is refused rather than recovered on the
    perfect shape.
    """

    if geometry is not None:
        return geometry.model()
    refusal = unbound_refusal(view)
    if refusal is not None:

    return view.built.fe_model

def read_persisted_display_field(dataset,field_key,*,frame=0,component=None):
    from ..post.fields import Field
    stored = dataset.field(field_key)
    descriptor = stored.descriptor
    local_frame=_persisted_frame(stored,frame)

        raise ValueError(f"{descriptor.label} has no saved component {component!r}")
    if component is not None:

        scalar = _artifact_scalar_rows(values,(),None,descriptor.provenance.get("scalar_sample_axes"))

    if len(scalar) != len(identifiers):

_PERFECT_STAGES = frozenset({"reference_static", "elastic_buckling"})


def _reference_record(dataset):
    """``(kind, record)`` of the saved reference geometry; absent means the mesh."""

    try:
        provenance = dataset.metadata("provenance")
    except (KeyError, AttributeError):
        provenance = {}
    if not isinstance(provenance, Mapping):
        raise ValueError(f"unrecognised saved result provenance {type(provenance).__name__}")
    if "reference_geometry" not in provenance:
        return "mesh_record", {}
    record = provenance["reference_geometry"]
    kind = record.get("kind") if isinstance(record, Mapping) else None
    if kind not in ("mesh_record", "solved_imperfect", "unbound_imperfect"):
        raise ValueError(f"unrecognised saved reference geometry {record!r}")
    return kind, record


def persisted_reference_positions(dataset, mesh, ordered_nodes, *, perfect_stage=False) -> np.ndarray:
    """Coordinates a saved result's displacements are measured from.

    The mesh record unless the artifact says it was solved on moved geometry,
    in which case the stored imperfect coordinates are used.  Artifacts written
    before the record existed have no key and read as the mesh.  An imperfect
    result whose geometry was not saved, or a record this reader does not
    understand, is refused.  ``perfect_stage`` marks a capacity stage that was
    solved on the unmoved model (reference static, elastic buckling).
    """

    kind, record = _reference_record(dataset)
    if kind == "unbound_imperfect":
        raise ValueError(
            "this result was solved on imperfect geometry that its artifact does not "
            "store; the deformed shape is not drawn on the perfect mesh"
        )
    if kind == "solved_imperfect" and not perfect_stage:
        ids = np.asarray(dataset.table(record["ids_table"]))
        stored = np.asarray(dataset.table(record["positions_table"]), dtype=float)
        if (
            ids.ndim != 1 or ids.dtype.kind not in "iu" or stored.shape != (len(ids), 3)
            or len(set(ids.tolist())) != len(ids) or not np.isfinite(stored).all()
        ):
            raise ValueError("the saved reference geometry is malformed; it is not used")
        row_of = {int(node): row for row, node in enumerate(ids)}
        try:
            return stored[[row_of[int(node)] for node in ordered_nodes]]
        except KeyError as error:
            raise ValueError(
                f"the saved reference geometry has no node {error.args[0]}; "
                "it does not match the result's mesh"
            ) from None
    return np.asarray([mesh.nodes[node] for node in ordered_nodes], dtype=float)

    from anypost import vector_magnitude, absolute_sample_max
